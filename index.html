Inside My Browser

This is a real web browser. It opens tabs, loads any site, blocks trackers, keeps history and bookmarks, and lives in the Start Menu like Chrome does. One person built it. Here is how it actually works.

~2,500 lines of our code  ·  on top of ~30 million lines of someone else's

01 Nobody builds a browser from scratch

When you imagine "building a browser", you probably picture writing the part that turns HTML into pixels — fonts, images, layout, video, encryption. That is one of the hardest things humans have ever written. Chrome's engine took thousands of engineers decades.

So we didn't write it. We borrowed it. Chrome's engine is free and open source; it's called Chromium. A toolkit called Electron hands you Chromium in a box plus the ability to write normal desktop-app code around it. Discord, VS Code and Slack are all built this way.

Everything hard about displaying a page was already solved. Everything about being a browser — tabs, an address bar, history, bookmarks, blocking ads — is the part we wrote.

That ratio above isn't cheating. It's how essentially all software works: you stand on a huge pile of existing work and add the part that didn't exist yet.

02 The two brains

The most important idea in the whole program. The app is split into two kinds of process — two separate running programs that talk to each other.

The main process is the manager. There is exactly one, and it's main.js. It is the only part allowed to touch the actual computer: read and write files, create windows, watch the network. Think of the manager of a restaurant — access to the safe, the keys.

The renderer processes are the dining room. They display things. The browser's own interface is one, and every web page you open is another. Ten tabs means roughly ten separate processes. Guests sit here. Guests don't go in the office.

Pages on the right never reach the left directly. Everything fits through the slot in the middle, and the slot only accepts a short, fixed list of requests.

Why split them? Two reasons. Crashes stay small — if a page runs out of memory and dies it takes one process with it, that tab shows an error and nothing else blinks. And websites are strangers — any page you visit runs code written by someone you have never met, so if that code found a bug in the engine and escaped, you want it landing in a locked room rather than in the process that can read your documents.

A web page can never touch your computer directly. It has to ask.

03 Asking: the slot in the door

If pages can't touch anything, how does the browser save your tabs when you close it? Through a deliberately tiny opening. Picture a locked door with a narrow slot: you can pass a note through, you cannot climb through. Our slot is preload.js, and it is short on purpose:

  • save my list of tabs, or give it back
  • add a page to history, or search history
  • list, add or remove a bookmark
  • read a setting, or change one
  • tell me when a download's progress changes

Notice what is not there: "read any file", "run any program", "delete this folder". Those were never offered, so they can never be requested. A door with no handle can't be picked.

That list lives in one small file, so anyone checking this browser's security can read it and know the complete set of things a page could ever ask for. Making the dangerous surface small enough to read in one sitting is often better security than making it clever.

04 A tab is a browser inside a browser

The browser window is itself a web page. The tab strip, the address bar, the buttons — that's HTML and CSS in index.html and styles.css, styled the way any website is.

So how do you put a website inside a website? A special element called a <webview>: like a frame with much stronger walls, with its own process and no access to the page containing it. Each tab is one; the five sidebar apps are five more.

This causes a problem that took real debugging to spot. Because a webview is a separate program, keys pressed inside a page never reach the browser's interface. Press Ctrl+F while reading an article and the shortcut simply wouldn't happen. The fix: the manager listens for keys before the page gets them, swallows the ones we've claimed, and re-sends them to the interface as messages. It works so smoothly you'd never guess — which is also why this kind of bug survives to release if nobody tests shortcuts while actually reading a page.

05 Where your stuff lives

Nothing is in the cloud. Nothing sits on anyone's server. It is all files on this computer, in the app's data folder.

tabs.jsonWhich tabs were open, so they come back
history.jsonPages you've visited — the last 5,000
bookmarks.jsonSaved pages, with their icons
settings.jsonEvery switch on the settings page
Partitions/main/Cookies and logins — what keeps you signed in

You can open the first four in Notepad. They're just text. Being able to read your own data is a feature.

One detail is more interesting than it looks: history isn't written to disk every time you visit a page. It's held in memory and saved every 15 seconds, plus when you quit. Saving on every navigation would rewrite the whole file dozens of times a minute for nothing. Writing less often is part of what makes it feel instant.

06 Not trusting web pages

Beyond the two-process split, the browser actively defends you. Every one of these is a switch on the settings page.

Tracker and ad blocking
Before any request leaves your computer it's checked against a list of known tracking and ad servers. A match is cancelled — the request never happens. A privacy feature that also happens to be the biggest speed-up available, because a shocking amount of a slow page is other people's analytics.
Tracking-tag stripping
Links ending in ?utm_source=… or fbclid=… carry tags that don't change the page; they exist to tell the site where you came from. About 25 of them are quietly removed.
HTTPS upgrade
http:// means anyone on the same Wi-Fi can read what you send. https:// is encrypted. Ask for the first, get the second.
Permissions default to no
A page asking for camera, microphone or location is refused instantly — you aren't even interrupted with a popup. Only notifications and clipboard are allowed, and both have switches.
WebRTC leak protection
There's a video-call feature in every browser that pages can abuse to learn your computer's address on the local network, even through a VPN. It's confined so they can't.
Downloads that won't run
Files save normally, but download a .exe and the Open button becomes Show: it opens the folder, not the program. Running something dangerous should take a deliberate step outside the browser.

07 Making it fast, and a ten-second mystery

Nothing loads until you look at it. The five sidebar apps used to all load the instant the browser opened. Now each waits until you first click it. Restored tabs work the same way: reopen with twelve tabs and only the one you were last looking at loads — the other eleven are names until clicked.

The window appears before it's finished. It shows immediately and fills in, because a window that appears instantly and populates feels far faster than a correct window half a second later. Perceived speed and actual speed are different things, and only one of them is what you feel.

Now the story. At one point the browser took ten full seconds to open. The obvious suspect was the tracker blocker, since it inspects every request. Instead of guessing, we measured: it cost 8.9 milliseconds across 577 requests, about 0.015ms each. Not the problem, not close.

So we loaded a completely blank page. No tabs, no sidebar, no blocking. Ten seconds. That result is what cracked it — if an empty page is just as slow, the problem cannot be in the code, because there is no code running. It was the folder: the project sat in OneDrive, where files are placeholders fetched on demand, and starting a browser reads thousands of files.

In the OneDrive folder10,337 ms
In a normal folder356 ms

Same code. 29× faster. The fix was moving a folder.

When something is slow, find out where before deciding what. And try the empty version — what a program does when it does nothing tells you what it costs before it even starts.

08 How it updates itself

There's no download page. The browser's own folder is a git repository connected to the copy on GitHub. Thirty seconds after it opens, and every four hours after, it quietly checks for new code and pulls it. Next time you open the browser you're running the new version — never asked, never interrupted, no progress bar.

One safety catch: it only accepts changes that stack cleanly on what's already there. If someone edited the files locally the update fails loudly rather than overwriting their work. A tool that silently destroys your changes in order to stay up to date is a bad tool.

10 Things that surprised us

Real bugs from building this. Every one generalises well beyond browsers.

The browser was showing an old Gmail

Sidebar Gmail looked years out of date. Not a layout problem: every browser announces what it is, and this one announced a version of Chrome from two years earlier, because that text had been typed by hand once and never updated. Google serves a stripped-down interface to browsers it thinks are ancient.

Anything you write down by hand will eventually become a lie. Ask the program what version it is instead of telling it.

A search box that silently did nothing

A security rule was added listing what the new tab page is allowed to do. It was slightly too strict and accidentally banned the page's own search box from submitting. No error, no warning — pressing Enter just did nothing.

Security rules break features silently. That's exactly what makes them dangerous to add without testing.

Links that opened nothing

Clicking an "opens in a new tab" link did nothing for weeks. The code handling it was listening for an event Electron had deleted three versions earlier. The code was perfectly correct — it was waiting for a phone call that would never come.

Code that stops being called doesn't announce itself. It just goes quiet.

Making it faster made it less safe

The tracker blocker was sped up by reading web addresses with a shortcut instead of parsing them properly. Four times faster — and it meant a tracker could disguise itself with a crafted address and walk straight past the blocklist. Caught only because the new version was tested against the old one rather than just timed.

Fast and correct are different goals, and speeding something up is a great way to quietly break it.

An app that couldn't find itself

The Start Menu shortcut launched and immediately reported it couldn't find the app. Both halves of the shortcut pointed at the same folder — except one had been quietly redirected somewhere else, so the same text meant two different places.

"It works on my machine" usually means the machine, not the code.

None of the individual pieces here are magic. A tab is a page inside a page. Saving is writing a file. Blocking an ad is checking a name against a list and saying no. What makes it a browser is that a few hundred small, understandable decisions are stacked up and made to work together — then hammered on until the rough edges are gone.

That's most software. Not one brilliant idea, but a lot of ordinary ideas arranged carefully, plus the patience to keep going after the tenth weird bug. The tenth weird bug is where you learn the most anyway.
